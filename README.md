# Narke

> **ソクラテス**　では、知らないのに知っていると思い込んでいたことを、あの子が探したり学んだりしようとしたと思うかね。自分は知らないのだと気づいて行き詰まり、知りたいと望むより前に。  
> **メノン**　そうは思いません、ソクラテス。  
> **ソクラテス**　それなら、しびれさせられたことは、あの子のためになったのだね。  
> **メノン**　そう思います。
>
> — プラトン『メノン』84c
>
> *οἴει οὖν ἂν αὐτὸν πρότερον ἐπιχειρῆσαι ζητεῖν ἢ μανθάνειν τοῦτο ὃ ᾤετο εἰδέναι οὐκ εἰδώς, πρὶν εἰς ἀπορίαν κατέπεσεν ἡγησάμενος μὴ εἰδέναι, καὶ ἐπόθησεν τὸ εἰδέναι; … ὤνητο ἄρα ναρκήσας;*

Narkeは、資料や概念について、あなたが本当に自分の言葉で説明できるかを問い続ける、対話型のレビューSkillです。

AIが作った提案書、読んでいる論文、勉強中の資格の範囲を渡すと、Narkeは第三者の目で資料を読み、問われうる箇所を洗い出します。そして、資料の具体的な文に結び付いた問いを投げます。あなたは自由に答えます。わからなければ「わからない」と答えます。対話の最後に、Narkeは理解度レポートを出します。レポートでは、正しい理解を認め、誤りを訂正し、問いごとに段階で評価します。残った「わからないこと」は、重要度順の一覧になります。

```text
資料を渡す → 始めの約束 → 問い（1回に最大10問） ⇄ 自由に答える・問いで深める → 理解度レポート
                                                                     ├ 回答ごとの段階評価と訂正
                                                                     └ わからないことリスト
```

## Narkeとは

Narke（ナルケー）は、シビレエイのことです。

古代ギリシャ語のνάρκη（narkē）は、「しびれ」と、しびれを起こす電気魚シビレエイを指します。シビレエイ科の学名*Narkidae*や属名*Narke*も、この語に由来します。

プラトンの『メノン』で、メノンはソクラテスをシビレエイにたとえます。問答の相手をしびれさせ、答えられなくするからです。ソクラテスは、こう応じます。

> シビレエイが、自分自身もしびれていて、それで他人もしびれさせるのなら、わたしはシビレエイに似ている。そうでないなら、似ていない。わたしは自分が答えに通じていて、他人を行き詰まらせるのではない。だれよりもわたし自身が行き詰まっているから、他人も行き詰まらせるのだ。
>
> — 『メノン』80c

Narkeは、その問いによって早すぎる理解を止め、不確実な点を明らかにし、対話を続けるという考えを表します。あぶのように前提を問い（『ソクラテスの弁明』30e）、シビレエイのように自明に見える理解を止め、産婆術のように理解が形になることを助けます（『テアイテトス』150b–c）。

ソクラテスと同じく、Narkeも答えを知っていて問うのではありません。レビューする側にわからないことがあれば、それも「わからない」と書きます。

## なぜNarkeが必要か

生成AIを使えば、資料を短い時間で作れます。その一方で、次のことが起きています。

- AIが作った資料を、よく理解しないままクライアントに使ってしまう。
- 資料を読んだだけで、わかった気になってしまう。
- 理解していない資料が、そのままクライアントに出てしまう。
- クライアントに出す前の上司のレビューに、時間がかかる。作成者が説明できない箇所を、上司が一つずつ問い直すことになる。

人に対しては、「わからない」「知らない」とは言いづらいものです。AIとの壁打ちなら、素直に「知らない」と言えます。Narkeは、この違いを使います。

## コンセプト：不知の自覚

Narkeの中心にある考えは、「不知の自覚」です。日本では「無知の知」と呼ばれることが多い考えです。

『ソクラテスの弁明』で、ソクラテスは、知者と評判の人と自分を比べて、こう述べます。

> この人は、知らないのに、何かを知っていると思っている。わたしは、知らないので、そのとおり知っているとも思っていない。
>
> — 『ソクラテスの弁明』21d（*οὗτος μὲν οἴεταί τι εἰδέναι οὐκ εἰδώς, ἐγὼ δέ, ὥσπερ οὖν οὐκ οἶδα, οὐδὲ οἴομαι*）

ここで区別されているのは、「知らないのに知っていると思っている状態」と、「知らないことを自覚している状態」です。ソクラテスは、無知を「知っている」と主張したのではありません。納富信留は、この姿勢を「無知の知」と呼ぶのは誤りであり、「不知の自覚」と呼ぶべきだと論じています（「ソクラテスの不知――「無知の知」を退けて」『思想』948号、2003年）。納富の用語では、「無知」は知らないのに知っていると思っている状態を、「不知」は知らないことを指します。この呼び方には異論もあります。Narkeは、原文の区別に合う「不知の自覚」を使います。

冒頭のエピグラフも、同じ区別を語っています。少年は初め、「知らないのに、知っていると思っていた」（ᾤετο εἰδέναι οὐκ εἰδώς）。しびれを経て、「知らないので、知っているとも思わなくなった」（ὥσπερ οὐκ οἶδεν, οὐδ᾽ οἴεται εἰδέναι、84a–b）。『弁明』21d と同じ言い回しです。

Narkeは、この区別を対話の仕組みにしています。

- **わかったふり（無知）を見つける。** 資料の言い回しを繰り返すだけの答えや、中身のない語で埋めた答えは、説明とは扱いません。
- **「わからない」（不知の自覚）を、わかったふりより高く評価する。** 正直な「わからない」からは学べます。わかったふりは、自分が知らないことに気づいていないので、学び始めることができません。
- **説明できるまで理解する。** 自分の言葉で、根拠と範囲まで説明できたとき、その問いを解決とします。

この考えは、レビューする側（AI）にも適用します。AIは、資料にも出典にもないことを推測で補いません。AIが作った資料の誤りをAIが補強すると、この対話は逆効果になるからです。

## ユースケース

| ユースケース | 対象 | Narkeが行うこと |
|---|---|---|
| 資格や概念の勉強 | 試験範囲・概念 | 定義・区別・適用を問い、説明できる状態にする |
| AIが作った資料の理解 | 提案書・報告書・スライド | 作成者が中身を説明できるかを問い、理解を深める |
| 資料の修正 | 根拠のない数字・食い違い・説明のない箇所 | ユーザーが説明できない理由が資料の欠陥にある箇所を見つけ、修正の候補にする |
| 上司のレビューの前の準備 | クライアントに出す資料 | 残った「わからないこと」と、答えるために必要な確認を一覧にする。上司のレビューの負担を減らす |
| 読解中の資料の理解 | 他人が書いた資料・論文 | 理解したつもりの箇所を問いに変える |

## 対話の進め方

1. **目的を確認します。** 対象・誰に説明するか・かけられる時間・資料の出どころを確かめます。
2. **問われうる箇所を、すべて洗い出します。** サブエージェントを使える環境では、資料だけを渡したサブエージェントが洗い出します。資料を作った会話の文脈を持たない読み手は、クライアントと同じ条件で資料を読むからです。
3. **始めの約束を伝えます。** わからないときは「わからない」と答えること。資料を見てもよいが、自分の言葉で答えること。対話の途中では正誤を言わず、最後のレポートで評価すること。
4. **問いを出します。** 1回に最大10問です。問いは資料の箇所ごとにまとめ、箇所の引用を付けます。答えや選択肢は示しません。答えを見て「それで合っている」と認めることと、自分で説明することは、別の力だからです。
5. **答えを問いで深めます。** 正誤は言いません。わかったふりには、避ける語を指定して言い直しを求めます。誤った答えには、正解を示す代わりに、自分で確かめられる問い（「この表から計算すると？」）を返します。
6. **前提を見直します。** 問いが資料の読み違いから出ていた場合は、レビューする側の誤りとして、その場で認めて直します。
7. **理解度レポートを出します。** 「ここまで」と言えば、いつでも終えられます。

## 理解度レポート

### 回答の評価

答えた問いごとに、次の段階で評価します。正しい理解は、どこが正しいかを具体的に書いて認めます。誤りは、根拠を示して訂正します。

| 評価 | 名前 | 基準 |
|---|---|---|
| 4 | 説明できた | 自分の言葉で、根拠と範囲まで正しく言えた |
| 3 | おおむね説明できた | 正しい。根拠・範囲・具体例の一部が欠ける |
| 2 | 不十分 | 方向は正しい。ただし、誤りか大きな欠けがある |
| 1 | わからない（不知の自覚） | 「わからない」と答えた |
| 0 | 思い込み（無知） | わかったふり、または根拠のない断定の誤り |
| — | 評価しない | 資料の欠陥のため、答えようがない問い |

### わからないことリスト

答えられないまま残った問いを、重要度順に一覧にします。一枚に収まる分量を目標にします。各項目には、次の内容を含めます。

- 問い
- 資料の該当箇所
- 状態（下の5つのいずれか）
- 答えるために必要な確認

Narkeは、問いが答えられないまま残る理由を、次の5つに区別します。

| 状態 | 意味 |
|---|---|
| 説明できない | 資料には書いてある。ユーザーがまだ自分の言葉で説明できない |
| 資料に説明がない | 答えに必要な内容が、資料のどこにもない |
| 根拠を確認できない | 資料に主張や数字はある。出所・計算・データを確かめられない |
| 判断が未決 | 誰かが決めないと答えが出ない |
| レビュー側の理解不足 | レビューする側が資料を読み違えた。または分野を判断できない |

レビューする側の理解不足を、ユーザーの無知とは扱いません。「資料に説明がない」「根拠を確認できない」も、ユーザーの知識の問題ではなく、資料の欠陥です。時間の都合で問わなかった論点は、リストに載せず、件数だけを書きます。

### レポートの後

ユーザーが選んだ場合に限り、次のことを行います。

- レポートをファイルに保存する。
- 復習の回を行う。評価が低かった問いを、レポートを読んだうえで自分の言葉で言い直す。
- 「資料に説明がない」「根拠を確認できない」の項目について、資料の修正案を作る。
- 評価の高い問いから想定問答を作る。答えはユーザーの言葉で記録します。AIが整えた模範解答に置き換えると、それはまた「本人が説明できないAIの文章」になるからです。

## 対話の例

検証用の架空の提案書（[tests/fixtures/sample-proposal.md](tests/fixtures/sample-proposal.md)）で、Claude Codeが実際に出力した対話の抜粋です。

**1回目の問い（10問のうち2問）**

> ### p.2「本日は、本提案での着手をご判断いただきたい」 — クライアントの部長として
>
> Q1. この資料で、部長に何を決めてほしいのですか。1〜2文で答えてください。
>
> ### p.3 の表「担当者4名 × 月20時間」 — クライアントの部長として
>
> Q4. この表の数字から計算すると、顧客情報の確認は年間で何時間になりますか。

**ユーザーの答え**

> Q1. 御社の問い合わせ対応を最適な形で効率化し、DXを推進するための判断です。  
> Q4. 1,200時間。

**2回目の深掘り（正誤は言わない）**

> Q11. 「最適」「効率化」「DX」の3語を使わずに、同じことを言い直してください。部長が本日どの行動を取るのかが分かる1文にしてください。  
> Q12. 4名 × 月20時間 を 12か月分で計算すると、何時間になりますか。その数字と p.2 の 1,200時間を並べると、どうなりますか。

**ユーザーの答え**

> Q11. 顧客情報を1つの画面で見られる仕組みを作ることに、今日着手してよいかを決めてもらう。  
> Q12. 960時間。p.2の1,200時間と合わない。資料の数字がおかしい。

**理解度レポート（抜粋）**

| Q | 問い | あなたの答え（要旨） | 評価 | 講評 |
|---|---|---|---|---|
| 1 | 部長に何を決めてほしいか | 顧客情報を1つの画面で見られる仕組みを作ることに、今日着手してよいかを決めてもらう | 4 | 正しい。決めてほしい行動（今日の着手判断）と対象（1画面の仕組み）が1文に入っている。最初の答え（「最適な形で効率化し、DXを推進する」）には、わかったふりのサインが3つ出ていた。曖昧な語（「最適な形で」）、定義の無い専門用語（「DX」）、決めてほしい行動が無いことである。深掘りの言い直しで解消した |
| 4 | 表から年間で何時間か | 960時間。p.2 の 1,200時間と合わない | 4 | 正しい。p.3 の表（4名 × 月20時間 × 12か月）から自分で計算し、p.2 との差 240時間に気づいた。最初の答えは「1,200時間」で、p.2 の数字をそのまま答えていた（根拠: 資料 p.2・p.3） |

## インストールと使い方

### Claude Code

1. このリポジトリをクローンします。

   ```bash
   git clone https://github.com/galeanthropy2/narke.git
   ```

2. `skills/narke` フォルダを、Claude Codeのユーザー用Skillフォルダにコピーします。

   ```bash
   cp -r narke/skills/narke ~/.claude/skills/narke
   ```

3. Claude Codeで、次のように呼び出します。

   ```text
   /narke proposal.md を詰めてほしい。来週クライアントに出す。時間は30分。
   ```

   「この資料、説明できるか質問攻めにして」のように頼んでも、Narkeが起動します。

対話の途中では、いつでも次の言葉を使えます。

| 言葉 | 動き |
|---|---|
| わからない | 正直な答えとして記録する |
| ヒント | 答えではなく、考える手がかりを1つだけ示す |
| 教えて | その問いだけを説明し、自分の言葉で言い直してもらう |
| パス | その問いを未回答のまま残し、次へ進む |
| 一覧 | 問いの状態を一覧で示す |
| ここまで | 対話を終え、理解度レポートを出す |

## 二つのレビュー視点

Narkeは、二つの視点から問いを作ります。二つの視点から得た問いを、同じ対話の中で扱います。

### フレッシュアイレビュー

資料の読み手が共有していない前提を確認します。説明が不足している箇所や、読み手が迷う箇所を探します。

### 哲学者レビュー

次の点を確認します。

- 用語の定義
- 概念の区別
- 隠れた前提
- 根拠と証拠
- 推論のつながり
- 反例
- 適用範囲

## 日本語の文体

日本語では、ASD-STE100の考え方を参考にします。次の方針を使います。

- 一文一義にする
- 文を短くする
- 主語を明示する
- 用語を統一する
- 曖昧な指示語を減らす
- 重要な条件や区別を省略しない

ASD-STE100は英語用の規格です。このプロジェクトは、公式の日本語版への準拠や規格適合を主張しません。
