# Narke

> **ソクラテス**　では、知らないのに知っていると思い込んでいたことを、あの子が探したり学んだりしようとしたと思うかね。自分は知らないのだと気づいて行き詰まり、知りたいと望むより前に。  
> **メノン**　そうは思いません、ソクラテス。  
> **ソクラテス**　それなら、しびれさせられたことは、あの子のためになったのだね。  
> **メノン**　そう思います。
>
> — プラトン『メノン』84c
>
> *οἴει οὖν ἂν αὐτὸν πρότερον ἐπιχειρῆσαι ζητεῖν ἢ μανθάνειν τοῦτο ὃ ᾤετο εἰδέναι οὐκ εἰδώς, πρὶν εἰς ἀπορίαν κατέπεσεν ἡγησάμενος μὴ εἰδέναι, καὶ ἐπόθησεν τὸ εἰδέναι; … ὤνητο ἄρα ναρκήσας;*

Narkeは、資料や概念について、あなたが自分の言葉で説明できるかを問い続ける、対話型のレビューSkillです。

AIの生成物を別のAIに敵対的にレビューさせても、良くなるのは資料で、人間の理解は変わりません。よくできた資料ほど、人間はわかったつもりになります。Narkeは、人間の側の認識を変え、理解を深めるきっかけを作ります。

```text
目的とモードの確認 → 問われうる箇所の洗い出し → 始めの約束
  → 問い（1回に1〜3問） ⇄ 自由に答える → 答えを見て次の問いを決める
  → 理解度レポート（回答ごとの段階評価と訂正／わからないことリスト）
```

わからないことの扱い方で、2つのモードを選べます。「潰す」は、わからないことをその場で1つずつ解決します。「書き出す」は、わからないことを記録するだけにとどめ、多くの論点に触れます。

## 概要

### Narkeとは

Narke（ナルケー）は、シビレエイのことです。

古代ギリシャ語のνάρκη（narkē）は、「しびれ」と、しびれを起こす電気魚「シビレエイ」を指します。シビレエイ科の学名*Narkidae*や属名*Narke*も、この語に由来します。

プラトンの『メノン』で、メノンはソクラテスをシビレエイにたとえます。問答の相手をしびれさせ、答えられなくするからです。ソクラテスは、こう応じます。

> シビレエイが、自分自身もしびれていて、それで他人もしびれさせるのなら、わたしはシビレエイに似ている。そうでないなら、似ていない。わたしは自分が答えに通じていて、他人を行き詰まらせるのではない。だれよりもわたし自身が行き詰まっているから、他人も行き詰まらせるのだ。
>
> — 『メノン』80c

Narkeは、その問いによって早すぎる理解を止め、不確実な点を明らかにし、対話を続けるという考えを表します。

ソクラテスには、シビレエイのほかにも、いくつかのあだ名（たとえ）があります。『ソクラテスの弁明』30e では、ソクラテスは国（アテナイ）を、大きいために動きの鈍い馬にたとえます。そして自分を、その馬を刺して目覚めさせる「あぶ」にたとえます。『テアイテトス』150b–c では、相手の中に生まれた考えを取り上げ、本物かどうかを吟味する自分の技を「産婆術」と呼びます。Narkeは、この三つのたとえを受け継ぎます。あぶのように前提を問い、シビレエイのように自明に見える理解を止め、産婆術のように理解が形になることを助けます。

Narkeも、模範解答を用意してから問うのではありません。問いは資料の中の手がかりから作り、答えを受け取ってから、資料と出典で確かめます。確かめるなかで、Narke自身も資料の誤りに気付きます。Narkeが判断できないことは、「レビュー側の理解不足」と書きます。

### なぜNarkeが必要か

生成AIを使えば、資料を短い時間で作れます。その一方で、次のことが起きています。

- AIが作った資料を、よく理解しないままクライアントに使ってしまう。
- 資料を読んだだけで、わかった気になってしまう。
- 理解していない資料が、そのままクライアントに出てしまう。
- クライアントに出す前の上司のレビューに、時間がかかる。作成者が説明できない箇所を、上司が一つずつ問い直すことになる。

人に対しては、「わからない」「知らない」とは言いづらいものです。AIとの壁打ちなら、素直に「知らない」と言えます。Narkeは、この違いを使います。

### コンセプト：不知の自覚

Narkeの中心にある考えは、「不知の自覚」です。日本では「無知の知」と呼ばれることが多い考えです。

『ソクラテスの弁明』で、ソクラテスは、知者と評判の人と自分を比べて、こう述べます。

> この人は、知らないのに、何かを知っていると思っている。わたしは、知らないので、そのとおり知っているとも思っていない。
>
> — 『ソクラテスの弁明』21d（*οὗτος μὲν οἴεταί τι εἰδέναι οὐκ εἰδώς, ἐγὼ δέ, ὥσπερ οὖν οὐκ οἶδα, οὐδὲ οἴομαι*）

ここで区別されているのは、「知らないのに知っていると思っている状態」と、「知らないことを自覚している状態」です。ソクラテスは、無知を「知っている」と主張したのではありません。納富信留は、この姿勢を「無知の知」と呼ぶのは誤りであり、「不知の自覚」と呼ぶべきだと論じています（「ソクラテスの不知――「無知の知」を退けて」『思想』948号、2003年）。納富の用語では、「無知」は知らないのに知っていると思っている状態を、「不知」は知らないことを指します。この呼び方には異論もあります。Narkeは、原文の区別に合う「不知の自覚」を使います。

冒頭のエピグラフも、同じ区別を語っています。少年は初め、「知らないのに、知っていると思っていた」（ᾤετο εἰδέναι οὐκ εἰδώς）。しびれを経て、「知らないので、知っているとも思わなくなった」（ὥσπερ οὐκ οἶδεν, οὐδ᾽ οἴεται εἰδέναι、84a–b）。『弁明』21d と同じ言い回しです。

Narkeは、この区別を対話の仕組みにしています。

- **Narkeは、内心の「知っているつもり」を判定しない。** それを判定できるのは本人だけである。問いに「わからない」と答えたとき、あなたは自分が知っているつもりだったことに、自分で気付く。Narkeは、そのきっかけを作る。
- **「わからない」を、なぞりや根拠のない断定より高く評価する。** 「わからない」は、自分の不知を自分で認めた答えである。そこから学び始められる。
- **説明できるまで理解する。** 自分の言葉で要点を説明できたとき、その問いを解決とする。

この考えは、レビューする側（AI）にも適用します。AIは、資料にも出典にもないことを、確かめたことのように書きません。AIの知識だけに頼る説明や訂正には「未確認」と付けます。AIが作った資料の誤りをAIが補強すると、この対話は逆効果になるからです。

### ユースケース

| ユースケース | 対象 | Narkeが行うこと |
|---|---|---|
| AIが作った資料の理解 | 提案書・報告書・スライド | 作成者が中身を説明できるかを問い、理解を深める |
| 上司のレビューの前の準備 | クライアントに出す資料 | 残った「わからないこと」と、答えるために必要な確認を一覧にする。上司のレビューの負担を減らす |
| 資料の修正 | 根拠のない数字・食い違い・説明のない箇所 | 説明できない理由が資料の欠陥にある箇所を見つけ、修正の候補にする |
| 資格や概念の勉強 | 試験範囲・概念 | 定義・区別・適用を問い、説明できる状態にする。教材があれば渡す。教材が無いとAIの知識に頼るので、説明と訂正に「未確認」が付く |
| 読解中の資料の理解 | 他人が書いた資料・論文 | 理解したつもりの箇所を問いに変える |
| エージェントによる資料の点検 | サブエージェントが作った資料 | 作成したサブエージェントに問い、説明できない箇所（資料の欠陥）を洗い出す |

## Skillの仕組み

### 対話の進め方

1. **目的とモードを確認する。** 対象・誰に説明するか・かけられる時間・資料の出どころ・モード（潰す／書き出す）を確かめる。依頼文から分かる点は聞かない。
2. **問われうる箇所を、すべて洗い出す。** サブエージェントを使える環境では、資料だけを渡したサブエージェントが洗い出す。資料を作った会話の文脈を持たない読み手は、クライアントと同じ条件で資料を読むからである。洗い出した箇所は、問う順序の台本ではなく、次に問う候補の一覧として使う。問わなかった箇所は記録に残り、次の対話で続けられる。
3. **始めの約束を伝える。** わからないときは「わからない」と答えること。資料を見てもよいが、自分の言葉で答えること。答える前に正解は言わず、段階評価は最後のレポートで示すこと。
4. **問いを出す。** 1回に1〜3問。既定は1問で、答えが互いに依存しない短い問いだけを2〜3問にまとめる。答えや選択肢は示さない。答えを見て「それで合っている」と認めることと、自分で説明することは、別の力だからである。
5. **答えを見て、次の問いを決める。** 説明できた答えには、一段深い問い（理由・使い方・反論への答え）か、次の論点を返す。なぞりの答えには、避ける語を指定して言い直しを求める。誤った答えには、正解を示す代わりに、自分で確かめられる問い（「この表から計算すると？」）を返す。「わからない」への対応は、モードで変わる。答えから新しい論点が見えたら、それも候補に加える。
6. **前提を見直す。** 問いが資料の読み違いから出ていた場合は、レビューする側の誤りとして、その場で認めて直す。
7. **理解度レポートを出す。** 「ここまで」と言えば、いつでも終えられる。

### 二つのモード

Narkeは、わからないことをどう扱うかで、二つのモードを使い分けます。依頼文から推定し、推定できなければ最初に聞きます。対話の途中で「潰す」「書き出す」と言えば、いつでも切り替えられます。

| | 潰す | 書き出す |
|---|---|---|
| 目的 | わからないことを、その場で1つずつ解決する | わからないことを見つけて、記録するだけにとどめる |
| 進め方 | 深さ優先。1つの論点を、説明できるまで掘る | 幅優先。多くの論点に触れ、わからない箇所の地図を作る |
| 「わからない」への対応 | 前提の論点へ降りる → ヒント → 説明 → 自分の言葉で言い直し | 理由（5つの状態）を決めて記録し、次の論点へ進む |
| 1回の問い | 1問が基本 | 独立した問いなら2〜3問 |
| 途中の正誤 | 論点を閉じるときに、適切な点と訂正を短く伝える | 言わない。最後のレポートで示す |
| 合う場面 | 勉強。資料を時間をかけて理解したいとき | 上司レビューの前。時間が少ないとき。資料の穴を探すとき |

どちらのモードでも、あなたが答える前に正解を言いません。段階評価（4〜0）は、最後のレポートまで見せません。

### 二つのレビュー視点

Narkeは、二つの視点から問いを作り、同じ対話の中で扱います。

**フレッシュアイレビュー**は、資料の読み手が共有していない前提を確認します。説明が不足している箇所や、読み手が迷う箇所を探します。

**哲学者レビュー**は、次の点を確認します。

- 用語の定義
- 概念の区別
- 隠れた前提
- 根拠と証拠
- 推論のつながり
- 反例
- 適用範囲

### 理解度レポート

#### 回答の評価

答えた問いごとに、次の段階で評価します。深掘りをした問いは、Narkeが説明・訂正する前の、最後の自力の答えで評価します。適切に理解できているところは、どこが適切かを具体的に書いて認めます。誤りは、根拠を示して訂正します。

「潰す」では、説明を聞いたあとに言い直して解決した問いもあります。その言い直しは評価に入れず、解決の仕方（自力／ヒント後／説明後／未解決）を別の列に書きます。

「適切に」かどうかは、まず資料に照らし、次に出典と確かめられる事実に照らして判断します。資料と事実が食い違うときは事実を優先し、資料の誤りを修正の候補にします。

| 評価 | 名前 | 基準 |
|---|---|---|
| 4 | 説明でき、発見がある | 3 に加えて、資料そのものの誤りに気付いた。または、資料に無い新たな前提や問題を見つけた |
| 3 | 説明できた（合格） | 自分の言葉で、要点を適切に説明できた。これが合格の線で、基本の満点 |
| 2 | 不十分 | 方向は適切。ただし、誤りか大きな欠けがある。資料の誤りに気付かず、資料どおりに説明した答えもここに入る |
| 1 | わからない | 「わからない」と答えた |
| 0 | なぞり・断定 | 資料の言い回しの繰り返し、中身のない語だけの答え、または根拠のない断定の誤り |
| — | 評価しない | 資料の欠陥のため、答えようがない問い |

自分の言葉で説明できれば 3 で、十分です。4 は、説明を超えて資料を良くする発見に付ける加点です。「資料に書かれていないので答えられない」「p.2 と p.3 の数字が合わない」のように、資料そのものの欠陥を見つけた答えも 4 です。

評価は、答えの形と中身に付けます。内心は判定しません。

#### わからないことリスト

答えられないまま残った問いを、重要度順に一覧にします。一枚に収まる分量を目標にします。各項目には、問いの番号・問い・資料の該当箇所・状態・答えるために必要な確認を書きます。

あなたの理解が適切でも、資料の側が未解決なら、その問いはリストに残ります。クライアントや上司には、まだ答えられないからです。「潰す」で解決した問いは、リストに載せません。時間の都合で問わなかった論点と、前提が未解決のため問わなかった論点（保留）は、リストに載せず、件数だけを書きます。

Narkeは、問いが答えられないまま残る理由を、次の5つに区別します。

| 状態 | 意味 |
|---|---|
| 説明できない | 資料には書いてある。ユーザーがまだ自分の言葉で説明できない |
| 資料に説明がない | 答えに必要な内容が、資料のどこにもない |
| 根拠を確認できない | 資料に主張や数字はある。出所・計算・データを確かめられない |
| 判断が未決 | 誰かが決めないと答えが出ない |
| レビュー側の理解不足 | レビューする側が資料を読み違えた。または分野を判断できない |

レビューする側の理解不足を、ユーザーの無知とは扱いません。「資料に説明がない」「根拠を確認できない」も、ユーザーの知識の問題ではなく、資料の欠陥です。

#### レポートの後

ユーザーが選んだ場合に限り、次のことを行います。

- レポートをファイルに保存する。
- 「書き出す」で終えた場合: 評価が 2 以下で重要度の高い問いを、「潰す」で続ける。
- 「潰す」で終えた場合: 復習の回を行う。説明を聞いて解決した重要な問いを、レポートを読んだうえで、もう一度自分の言葉で言い直す。
- 「資料に説明がない」「根拠を確認できない」の項目について、資料の修正案を作る。
- 評価が 3 以上の問いと、「潰す」で解決した問いから想定問答を作る。答えはユーザーの言葉で記録する。AIが整えた模範解答に置き換えると、それはまた「本人が説明できないAIの文章」になるからである。

### 対話の例

架空の提案書（顧客情報を名寄せして、問い合わせ対応を効率化する提案）を、「潰す」で問うときの対話の例です。流れを示すために手で書いた例で、実際の出力ではありません。
1往復に1問ずつ出し、答えを見て次の問いを決めています。

**1往復目**

> **資料全体 — クライアントの部長として**
>
> Q1. この資料で、部長に何を決めてほしいのですか。1〜2文で答えてください。

> **ユーザー**　御社の問い合わせ対応を最適な形で効率化し、DXを推進するための判断です。

**2往復目**（なぞりの答えなので、避ける語を指定して言い直しを求める。正誤は言わない）

> Q2. （Q1 の続き）「最適」「効率化」「DX」の3語を使わずに、部長が今日どう答えればこの提案が前に進むのかを、1文で書いてください。

> **ユーザー**　顧客情報を1つの画面で見られる仕組みを作ることに、今日着手してよいかを決めてもらう。

**3往復目**（要旨を説明できたので、台帳の「最も弱い箇所」へ進む）

> **p.3 の表「担当者4名 × 月20時間」 — 現場の管理者として**
>
> Q3. この表の数字から計算すると、顧客情報の確認は年間で何時間になりますか。

> **ユーザー**　1,200時間。p.2に書いてあるとおり。

**4往復目**（誤りなので、正解を示さず、自分で確かめられる問いを返す）

> Q4. （Q3 の続き）p.3 の表の「担当者4名 × 月20時間」を、12か月分で計算してください。いくつになりますか。

> **ユーザー**　960時間。

**論点を閉じる**（「潰す」では、自分で答えたあとに、適切な点と訂正を短く伝える）

> Q3〜Q4 の論点（年間の確認時間）は、ここで閉じます。  
> 適切な点: p.3 の表から 960時間を自分で計算しました。  
> 訂正: p.2・p.5 の「1,200時間」は、p.3 の表（960時間）と合いません。部長はこの差に気づきます。資料の修正候補として記録します（根拠: 資料 p.2・p.3・p.5）。

「書き出す」では、Q4 の答えを記録したあと、論点を閉じる言葉を付けずに次の論点へ進みます。訂正は、最後のレポートで示します。

**理解度レポート（抜粋）**

深掘りの答え（Q2・Q4）は、元の問い（Q1・Q3）の評価にまとめます。評価は、Narkeが訂正する前の、最後の自力の答えで付けます。

| Q | 問い | あなたの答え（要旨） | 評価 | 解決 | 講評 |
|---|---|---|---|---|---|
| 1 | 部長に何を決めてほしいか | 顧客情報を1つの画面で見られる仕組みを作ることに、今日着手してよいかを決めてもらう | 3 | 自力 | 適切。決めてほしい行動（着手の判断）と対象（1画面で見る仕組み）が1文に入っている。最初の答えは「最適」「DX」という中身のない語だけで、何を決めるのかが入っていなかった |
| 3 | 年間の確認時間は何時間か | 1,200時間（p.2 のとおり）→ 深掘り後: 960時間 | 2 | ヒント後 | 計算の問いで 960時間に到達したのは適切（4名 × 月20時間 × 12か月、根拠: 資料 p.3）。p.2・p.5 の「1,200時間」と 240時間ずれている点は、自分からは指摘しなかった |

### 限界

- 評価はAIが付ける。同じ答えに、毎回同じ評価が付くとは限らない。評価が一致する割合は、まだ測っていない。
- 資料の誤りにAIも気付かなければ、資料どおりの答えを高く評価してしまう。
- 「わからない」が、考えた末の答えか、考えることを避けた答えかは区別しない。区別できるのは本人だけである。
- 資料が無い勉強では、論点・説明・訂正がAIの知識に頼る。教材を渡すと、確かめられる範囲が広がる。
- 「潰す」では、論点を閉じるときに訂正を伝える。そのため、そのあとの問いには、訂正を聞いた影響が入る。評価は自力の答えで付けるが、影響を完全には除けない。
- 時間の目安（「書き出す」は1問あたり約1分、「潰す」は1論点あたり3〜5分）は見積もりで、実測していない。

## 導入と使い方

### インストール

`skills/narke` フォルダ全体（`references` を含む）を、各環境のSkillフォルダに置きます。

**Claude Code**

```bash
git clone https://github.com/galeanthropy2/narke.git
cp -r narke/skills/narke ~/.claude/skills/narke
```

**Codex**

Codexに、次のように依頼します。

```text
$skill-installer https://github.com/galeanthropy2/narke/tree/main/skills/narke をユーザー共通でインストールしてください。
```

手動で置く場合は、`skills/narke` を `~/.agents/skills/narke` にコピーします。Codexの版によっては `~/.codex/skills/narke` が配置先です。両方に重複して置かないでください。インストール後に認識されなければ、Codexを再起動します。

**更新**

コピーしたSkillは、リポジトリの更新に追従しません。`git pull` の後、同じ配置先へもう一度コピーします。

### 呼び出し方

Claude Codeでは `/narke`、Codexでは `$narke` で呼び出します。続けて、資料のパスか添付と、目的を書きます。

```text
/narke proposal.md を詰めてほしい。AIで作った資料で、来週クライアントに出す。時間は30分。わからないところは書き出すだけでいい。
```

モードを書かなければ、Narkeが依頼文から推定します。推定できなければ、最初に聞きます。

Claude Codeでは、「この資料、説明できるか質問攻めにして」「この概念のわからないところを潰したい」のように頼んでも、Narkeが起動します。

### 対話中に使える言葉

| 言葉 | 動き |
|---|---|
| わからない | 正直な答えとして記録する |
| ヒント | 答えではなく、考える手がかりを1つだけ示す |
| 教えて | その問いだけを説明し、自分の言葉で言い直してもらう |
| パス | その問いを未回答のまま残し、次へ進む |
| 一覧 | 問うた問いと、答えたかどうかを示す（評価は示さない） |
| 潰す | モードを「潰す」に切り替える。「Q4 は潰したい」なら、その論点だけを潰す |
| 書き出す | モードを「書き出す」に切り替える |
| ここまで | 対話を終え、理解度レポートを出す |

### 対応環境

| 環境 | 状態 |
|---|---|
| Claude Code | 起動から理解度レポートまで、動作を確認済み（2026年10月） |
| Codex | `$narke` での起動を確認済み（2026年10月） |

上の確認は、1回に最大10問を出していた版で行いました。1〜3問ずつの問いと二つのモードは、そのあとの変更で入りました。この変更後の動作は、まだ確かめていません。

Skill本体は `SKILL.md` を中心に、環境に依存しない形で書いています。サブエージェントを使えない環境では、Narke自身が問われうる箇所を洗い出します。Codexの配置先と呼び出し方は、[OpenAI公式のSkillドキュメント](https://learn.chatgpt.com/docs/build-skills)に基づきます。

### ファイル構成

```text
skills/narke/
├── SKILL.md                     対話の進め方
└── references/
    ├── question-map.md          問われうる箇所を洗い出すサブエージェントへの指示文
    ├── perspectives.md          二つの視点の問い・わかったふりのサイン・深掘りの問い
    └── report.md                理解度レポートの形と評価の段階
```

### 日本語の文体

日本語では、ASD-STE100の考え方を参考にします。次の方針を使います。

- 一文一義にする
- 文を短くする
- 主語を明示する
- 用語を統一する
- 曖昧な指示語を減らす
- 重要な条件や区別を省略しない
- 地の文は敬体（です・ます）、箇条書き・表・手順の項目は常体で書く

ASD-STE100は英語用の規格です。このプロジェクトは、公式の日本語版への準拠や規格適合を主張しません。
