# Narke

理解したつもりの内容を具体的な問いに変え、最後に「わからないことリスト」を作る対話型レビューSkillです。

> **開発状況：Claude Code版を実装・検証済み**  
> Skill本体は [skills/narke/](skills/narke/) にあります。Claude Codeでの動作を検証しました。Codexへの対応は未検証です。

## 背景

生成AIで作った資料には、次の問題があります。

- 作成者が中身をよく理解しないまま、資料をクライアントに出してしまう。
- 作成者が、資料を読んだだけで理解したつもりになる。
- クライアントに出す前の上司のレビューに、時間がかかる。上司は、作成者が説明できない箇所を一つずつ問い直すことになる。

人に対して「わからない」「知らない」と言うことは難しい。AIとの対話では、素直に「知らない」と言いやすい。Narkeは、この違いを使います。

## 目的

Narkeは、第三者の目で資料を読み、ユーザーに問いを投げます。ユーザーが資料を自分の言葉で説明できるかを、網羅的かつ徹底的に確かめます。

Narkeが目指す状態は、次のとおりです。

- 曖昧なままにしていた内容を、ユーザーが説明できる。
- ユーザーが説明できない箇所のうち、資料の欠陥による箇所を修正できる。
- 上司やクライアントの前に出す前に、残る「わからないこと」が一覧になっている。

## コンセプト：無知の知

Narkeの中心にある考えは「無知の知」です。

- わかったふりをしない。
- 自分が知らないことに気づいていない箇所を、問いによって気づけるようにする。
- 曖昧にしたままの内容を、説明できるまで理解する。

この考えは、レビューする側（AI）にも適用します。AIは、資料にも出典にもないことを推測で補いません。AIが資料を理解できない箇所は、AI自身の理解不足として扱います。

## ユースケース

| ユースケース | 対象 | Narkeが行うこと |
|---|---|---|
| AIで作った資料の確認 | 提案書・報告書・スライド | 作成者が説明できるかを問う。資料の欠陥を見つける |
| 上司のレビューの前の準備 | クライアントに出す資料 | 未解決の問いと、答えるために必要な確認を一覧にする |
| 読解中の資料の理解 | 他人が書いた資料・論文 | 理解したつもりの箇所を問いに変える |
| 資格や概念の勉強 | 試験範囲・概念 | 定義・区別・適用を問い、説明できる状態にする |

## Narkeとは

Narkeは、ユーザーが作成した資料、検討中の資料、読解中の資料を対象にします。資料がない場合は、概念や資格の試験範囲を対象にします。対話を通じて、次の状態を区別します。

| 状態 | 意味 |
|---|---|
| 説明できない | 資料には書いてある。ユーザーがまだ自分の言葉で説明できない |
| 資料に説明がない | 答えに必要な内容が、資料のどこにもない |
| 根拠を確認できない | 資料に主張や数字はある。出所・計算・データを確かめられない |
| 判断が未決 | 誰かが決めないと答えが出ない |
| レビュー側の理解不足 | レビューする側が資料を読み違えた。または分野を判断できない |

レビューする側の理解不足を、ユーザーの無知とは扱いません。

## 二つのレビュー視点

### フレッシュアイレビュー

資料の読み手が共有していない前提を確認します。説明が不足している箇所や、読み手が迷う箇所を探します。

### 哲学者レビュー

次の点を確認します。

- 用語の定義
- 概念の区別
- 隠れた前提
- 根拠と証拠
- 推論のつながり
- 反例
- 適用範囲

二つの視点から得た問いを、同じ対話の中で扱います。

## 対話の流れ

1. 資料とレビューの目的を確認します。
2. 資料の問われうる箇所を、すべて洗い出します。サブエージェントを使える環境では、資料だけを渡したサブエージェントが洗い出します。資料を作った会話の文脈を持たない読み手は、クライアントと同じ条件で資料を読むからです。
3. 資料中の具体的な文や節に結び付けて、2〜4個程度の問いを出します。模範解答や選択肢は示しません。
4. 回答を受けて、問いを深掘りします。資料の言い回しを繰り返すだけの答えは、「わかったふり」として問い直します。
5. 解決した問いを未解決の問いから外します。
6. ユーザーの前提とレビューする側の前提を、必要に応じて再検討します。
7. 最後に、残った「わからないこと」を重要度順にまとめます。

## 最終出力

最終出力は、一枚に収まる分量を目標にします。各項目には、次の内容を含めます。

- 問い
- 資料の該当箇所
- 状態（上の5つのいずれか）
- 答えるために必要な確認

解決済みの問いは、未解決のリストに残しません。

リストを出した後、ユーザーが選んだ場合に限り、次のことを行います。

- リストをファイルに保存する。
- 「資料に説明がない」「根拠を確認できない」の項目について、資料の修正案を作る。
- 解決した問いから想定問答を作る。答えはユーザーの言葉で記録します。AIが整えた模範解答に置き換えると、それはまた「本人が説明できないAIの文章」になるからです。

## インストールと使い方

### Claude Code

1. このリポジトリをクローンします。

   ```bash
   git clone https://github.com/galeanthropy2/narke.git
   ```

2. `skills/narke` フォルダを、Claude Codeのユーザー用Skillフォルダにコピーします。

   ```bash
   cp -r narke/skills/narke ~/.claude/skills/narke
   ```

3. Claude Codeで、次のように呼び出します。

   ```text
   /narke proposal.md を詰めてほしい。来週クライアントに出す。時間は15分。
   ```

   「この資料、説明できるか質問攻めにして」のように頼んでも、Narkeが起動します。

対話の途中では、いつでも次の言葉を使えます。

| 言葉 | 動き |
|---|---|
| わからない | 原因を5つの状態のどれかに分け、次の確認を示す |
| ヒント | 答えではなく、考える手がかりを1つだけ示す |
| パス | その問いを未回答のまま残し、次へ進む |
| 一覧 | 問いの状態を一覧で示す |
| ここまで | 対話を終え、わからないことリストを出す |

## 日本語の文体

日本語では、ASD-STE100の考え方を参考にします。次の方針を使います。

- 一文一義にする
- 文を短くする
- 主語を明示する
- 用語を統一する
- 曖昧な指示語を減らす
- 重要な条件や区別を省略しない

ASD-STE100は英語用の規格です。このプロジェクトは、公式の日本語版への準拠や規格適合を主張しません。

## 名前の由来

古代ギリシャ語のνάρκη（narkē）は、「しびれ」と、しびれを起こす電気魚を指します。学名の*Narke*も、この語に由来します。

プラトンの『メノン』では、ソクラテスは相手を立ち止まらせる電気魚にたとえられます。Narkeは、その問いによって早すぎる理解を止め、不確実な点を明らかにし、対話を続けるという考えを表します。

あぶのように前提を問い、シビレエイのように自明に見える理解を止め、産婆術のように理解が形になることを助けます。
